# Deployment — Render (API) + Vercel (frontend) + MongoDB Atlas

> Target: free tiers to start. Backend on **Render** (`render.yaml`), frontend on **Vercel** (`vercel.json`), database on **MongoDB Atlas**. Billing setup is in `docs/BILLING.md`.
> Railway still works later (`railway.json`, `nixpacks.toml`, `Dockerfile` are kept on Node 22 with the same start flags) — switching is only setting the same env vars there.

## Architecture

```
Browser ──HTTPS──▶ Vercel (static React build)
   │
   └──HTTPS + WSS──▶ Render web service (Express API + WebSockets, Node 22)
                         ├─▶ MongoDB Atlas (data)
                         ├─▶ Render Key Value / Redis (notification queue, login throttling)
                         ├─▶ Groq (AI), Cloudinary (images), Resend (email)
                         └─◀ Polar webhooks (billing)
```

## Free-tier trade-offs (know these before inviting users)

- Render free **sleeps after ~15 min idle**; the next request waits up to a minute. Open chat sockets drop when it sleeps.
- Polar webhooks that hit a sleeping instance are retried by Polar; `/billing` also self-repairs via `/sync`.
- 0.1 CPU: code submissions are capped (30/day free, 300 Pro) partly for this reason.
- Upgrade to a paid instance (Render Starter ≈ $7/mo or Railway Hobby $5/mo) before a real pilot.

## 1. MongoDB Atlas

1. Create a free **M0** cluster, region **eu-central (Frankfurt)** to sit next to Render's Frankfurt region.
2. Database Access → create a user with a strong password (readWrite on the app database is enough).
3. Network Access → allow `0.0.0.0/0` (Render free has no static outbound IP). The password is the protection, so make it long.
4. Copy the connection string → this is `MONGO_URI`. The app uses the `DevsBlog` database.
5. Seed content once from your machine against the Atlas URI:
   `npm run seed:roadmap`, `npm run seed:challenges`, `npm run seed:concepts`, `npm run seed:rubrics`, and the exam banks (`node backend/seeders/examSeeder.js`).

## 2. Redis (optional but recommended)

- Render → New → **Key Value** (free, 25 MB, same region). Copy its **internal URL** → `REDIS_URL`.
- Free Key Value data is lost on restart; that only drops pending notifications.
- Or skip Redis entirely: set `REDIS_ENABLED=false` (no notifications; login throttling falls back to off).

## 3. Render (backend)

1. Push to GitHub, then Render → New → **Blueprint** → pick the repo. It reads `render.yaml`:
   free plan, Frankfurt, Node 22, `npm ci`, start `npm start` (= `node --no-node-snapshot backend/server.js`), health check `/healthz`.
2. Fill every variable marked "sync: false" in the dashboard (table below). `JWT_Secret` and `JWT_REFRESH_SECRET` are generated by Render.
3. Deploy. Check `https://<service>.onrender.com/healthz` → `{"status":"ok"}`.
4. Check the code runner: `GET /api/challenges/submissions/runner` (logged in) should say `"backend":"isolated-vm"`. If it says `"disabled"`, the sandbox did not build — submissions are refused on purpose (see Troubleshooting).

## 4. Vercel (frontend)

1. Import the repo; framework preset **Vite**; build `npm run build`; output `dist`.
2. Environment variables (Production):
   - `VITE_API_BASE_URL` = `https://<service>.onrender.com`
   - `VITE_WS_URL` = `wss://<service>.onrender.com`
   (`.env.production` already points at `devs-website.onrender.com`; the Vercel values win if set.)
3. After the first deploy, copy the Vercel URL into Render's `FRONTEND_URL` (no trailing slash) and redeploy the backend — CORS, cookies, OAuth redirects and the WebSocket origin check all use it.
4. Preview deployments have different URLs; add any you need to `WS_EXTRA_ORIGINS` (comma-separated). REST CORS only allows `FRONTEND_URL`.

## 5. OAuth, email, billing

- Google / GitHub OAuth apps: add the production callback/redirect URLs that point at the Render API.
- Resend: verify the sending domain.
- Polar: create the **production** token, product and webhook (`https://<service>.onrender.com/api/billing/webhook`, events `subscription.*`) — never reuse sandbox values. See `docs/BILLING.md`.

| `REDIS_URL` *or* `REDIS_ENABLED=false` | yes | One of the two. `REDIS_HOST/PORT/PASSWORD` still work for local Docker. |
| `CLOUDINARY_*` | for uploads | Cloud name, key, secret. |
| `RESEND_API_KEY` | for email | Password reset etc. |
| `GOOGLE_CLIENT_ID`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET` | for OAuth | |
| `GEMINI_API_KEY` | optional | Only if Gemini features are used. |
| `POLAR_*`, `BILLING_ENFORCED` | for billing | See `docs/BILLING.md`. Keep `BILLING_ENFORCED=false` during the pilot. |

## Production safety behaviour (built in)

- **Health:** `/healthz` pings MongoDB with a 3 s timeout; 200 or 503. Answered before Express, so maintenance mode and auth never affect it.
- **Graceful shutdown:** on SIGTERM (every deploy/sleep) the server stops taking new requests, closes sockets with 1001, finishes in-flight work, then closes the worker, Redis and MongoDB; forced exit after 10 s.
- **Code runner fails closed:** without the isolated-vm sandbox, production refuses submissions (503) instead of running strangers' code with server privileges. Run-in-browser keeps working.
- **Submission cap:** 30/day free, 300/day Pro, atomic under concurrency.
- **WebSocket origin check:** only `FRONTEND_URL` (+ `WS_EXTRA_ORIGINS`) may open a socket from a browser.
- **No secrets in images:** `.dockerignore` excludes every `.env`.

## Troubleshooting

- **Runner says `"disabled"`**: isolated-vm is an *optional* dependency, so a failed native build does not fail the deploy. Check the build log for `isolated-vm` errors (it needs Node 22 and a C++ toolchain, which Render's native environment provides). Also confirm the start command includes `--no-node-snapshot` (`npm start` does).
- **CORS errors / cookies not sticking**: `FRONTEND_URL` must exactly match the Vercel origin (scheme + host, no slash). The refresh cookie is `SameSite=None; Secure`, which requires HTTPS on both ends.
- **WebSocket refused (401 on upgrade)**: the page's origin isn't `FRONTEND_URL` or in `WS_EXTRA_ORIGINS`.
- **Notifications never arrive**: Redis is disabled or `REDIS_URL` is wrong; the log says "Redis disabled — NotificationWorker not started" in the first case.
- **First request is slow**: the free instance was asleep. Expected.
